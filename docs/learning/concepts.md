## Collecting web pages: keys, raw landing and content hashes

*Learned 2026-11-19, while settling data collection choice 1.*

When I save a link in Mind Dump, the API writes one row to Postgres straight away, so the app says "Saved" in milliseconds, and a background worker fetches the page later. Each item has a surrogate primary key, `item_id`, which Postgres makes up and every other table points at; because nothing about the page created it, nothing that happens to the page can change it. The normalised URL is the business key: it is how the outside world recognises the same thing again, and a unique index on it means the database itself rejects a duplicate with a 409, even when two saves race. That works because adding the index entry is the check, so there is no gap between "look" and "write" for a second request to slip through. I don't make the URL the primary key because URLs change, notes have none, and every pointing row would have to carry a copy of it. Before parsing anything, the worker lands the raw response, gzipped, in an append-only store, with a fetch record of the time, requested and final URL, HTTP status, content type, size, hash and storage key. A parser bug or a dead page therefore never costs me the source, I can re-process offline from the same input every time, and a 404 can never overwrite the last good copy. Two SHA-256 hashes then decide the work: identical raw bytes means store no new file, and identical article text means skip re-chunking and re-embedding, which is where the real cost is. They are separate because a rotating ad changes the bytes but not the article.

## Database migrations

*Learned 2026-11-19.*

A migration is one numbered, permanent step that changes the database's structure, kept in git like code. Every database the app runs against (my Mac, CI's fresh one, later Azure) replays the steps in order, so they all end up the same shape instead of drifting apart through hand edits. My runner keeps a `schema_migrations` table of the steps already applied and runs only the missing ones, which makes running it again safe: it is idempotent. An applied migration is never edited, because databases that already ran it would never see the change; a fix is always a new numbered file.

## Idempotent jobs: at-least-once, upserts and the orphan trap

*Learned 2026-11-19 and 2026-11-20, while settling data collection choice 2.*

A job queue can promise that every job runs at least once, but never exactly once, because a worker that dies cannot say how far it got; its lease runs out and another worker runs the job again from the start. So the order of a job's writes matters. If it marks the job done before doing the work, a crash loses the work silently: the item says "ready" and is never searchable, which is at-most-once and the worst failure for a second brain. If it does the work first and marks done last, a crash means the work runs twice, which is at-least-once: loud, visible, and fixable. The industry answer is at-least-once delivery plus idempotent processing, which together give effectively-once. A plain INSERT is not idempotent, because a retry duplicates every chunk. An upsert on the chunk's business key, `(item_id, chunk_index)`, fixes retries, since each chunk lands on its twin, but it only touches the keys it is given; when a re-process makes fewer chunks than before, the old extra chunks stay behind with stale text. That is the orphan trap. So the worker replaces the whole set instead: delete the item's chunks and insert the new ones. That is safe because chunks are derived data that can always be rebuilt from the raw file, and history belongs in the source layer, not in the derived one. A delete followed by an insert is two writes, though, and a crash between them would leave the item with no chunks until the retry. So both run inside one transaction, together with marking the job done: a transaction is all or nothing, like a bank transfer. If the worker dies before COMMIT, Postgres rolls everything back, the old chunks are still there, and the lease runs out and the job runs again. Other readers never see the middle, only the old set and then the new one. The worst case goes from missing to briefly out of date, and "done but no chunks" becomes impossible, because the queue lives in the same Postgres as the data.

## Branch flow: trunk-based, build once, deploy many

*Learned 2026-11-19, while deciding P0 (D29).*

Mind Dump uses trunk-based development: one long-lived branch, `main`, fed by short-lived branches through pull requests. Each merge builds one image, the packaged app, frozen. It goes to DEV first, and after an approval that same image goes to PROD, so the image I tested is, byte for byte, the image I ship. An environment is the place an image runs, with that place's own database, secrets and settings; the image stays identical and each environment hands it different settings at start-up. With environment branches (`develop` to DEV, `main` to PROD), each branch builds its own image, so PROD runs a build nobody tested. Usually the two builds match, but a new base image or tool version can make them differ, and that is when code that "passed in DEV" breaks PROD. Environment branches are still a fair choice for teams that release in scheduled batches, want git to show what is in PROD, or need the merge as an audit record, and they can still build once; the risks to watch are rebuilding per environment and forgetting hotfix merge-backs.

## The merge gate and fix-forward hotfixes

*Learned 2026-11-19, while deciding P0 (D29).*

Nothing reaches `main` except through a pull request whose CI checks pass. That covers lint, tests, the image build and a smoke test for the backend, plus an Xcode build for the app. I require no approvals because I work alone, and GitHub doesn't let you approve your own PR, but the PR still matters, because it is where CI runs and what leaves a record. GitHub push protection blocks known secret formats before they ever reach the repository, which is stronger than a check that finds them afterwards. A direct push to `main` is refused by two independent rules, the PR rule and the required checks, which is defence in depth. Hotfixes fix forward: branch from `main`, PR, CI, merge, then the one new image goes DEV, approval, PROD, and DEV is never skipped. That only works if `main` is always releasable, so unfinished work is either not merged or sits behind a feature flag that is off, and the PR template asks about it every time. If unflagged work turns up during a hotfix, I revert it rather than ship it. I never hand-edit PROD, because a server running code that exists in no image and no commit drifts from the record, and the next deploy silently undoes the fix. The whole gated path costs minutes; CI runs in under one.
