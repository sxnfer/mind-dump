# M6: Notch app and live status

> Read this when: you are working on M6, or need its tasks and done-when list.

**Goal:** the full notch experience.
**Decisions needed:** D11, D23.
**Tasks:**
- [x] The island in SwiftUI: idle, peek (pointer over the notch), compact (a status pill) and expanded (the panel), with one black body whose width, height and corner each follow their own spring (slice 1, `app/MindDump/Island/`). The springs are islandcn's measurements of the iPhone's island (`IslandMotion.swift`). Not yet: split (two activities at once).
- [x] Respect the system "Reduce motion" setting: the shape eases for 0.2 s with no overshoot, and content cross-fades with no blur or scale (slice 1).
- [x] Live status per item, by polling (D11): the pill goes "Saved", "Reading page", "Ready", or says the page could not be read (slice 1). Server-Sent Events wait until the island shows several items.
- Left panel: search, filter chips, list. Right panel: overview. Library and + buttons.
- Global shortcut to open the panel.
- [x] One-box capture, typed or pasted (slice 1): one input sorts a web address into a link and anything else into a note, in the app, and says which before Return. Dropping a file on the notch came in slice 5 (one PDF, PNG or JPEG); the box itself still takes only text. One-box capture: one input that takes anything (type, paste or drop) and sorts it for the user into a note, link or file. It replaces M1's clipboard check and its "Write a note instead" choice. Open design question for San: sort in the app or behind the API? (Raised by San on 2026-11-20 after testing M1; parked until after 26 Nov, because the proof track is backend only.)
- [x] Ask from the island (slice 2, branch `m6-ask`, `app/MindDump/Ask/`): the panel has two modes, Capture and Ask, with a pill that slides between them (Tab or a click). Ask streams `POST /ask?stream=true` (Server-Sent Events): a status line ("Thinking", "Searching “…”", "Reading an item"), then the answer at a steady pace with `[c:…]` markers shown as small numbers, then numbered sources that expand to show the passage. Follow-ups continue the conversation; ⌘N or "New question" starts a new one. Closing mid-answer cancels it (the backend saves nothing). Errors (backend down, no key, daily cap, rate limit, an error mid-stream) stay in the panel in plain words. Not from your items: a clear notice and no sources. Debug builds can play canned answers (`MD_ASK_FIXTURE=1`), so the UI was built and measured without paying for model calls.
- [x] Measure smoothness (slice 1): debug builds time every frame of every transition and print the late ones (`Support/Debug.swift`); `MD_MOTION_SCALE=8` gives slow motion, and the app can film its own window. Measured on a 120 Hz display: no late frame in any transition, except one late frame about 240 ms into the first open after launch (AppKit's first text focus). Instruments not used yet.
- Not yet after slice 2: older turns of a conversation (the panel shows only the latest question and answer), Discuss from a source row, search without asking, and the "open" arrow on link sources was not clicked in testing. Measured on a 120 Hz display with debug builds (an idle panel here shows 0 to 2 late frames per 1.3 s on its own): switching modes with a short or no answer, opening and closing a source row, the sources coming in and reopening a long answer show 0 or 1 late frame. Not yet clean: a stream shows a few single late frames (about one every 2 s, including one when the first words appear); switching away from, or closing, a long answer drops 1 to 3 frames; closing while an answer streams makes the collapse's first frame 8 to 21 ms late (see the known issue below); typing drops about one frame per key in both modes; the first open after launch still has its one late frame (AppKit's first text focus).
- Known issue (slice 2): closing while an answer streams. It was 13 to 38 ms late in the collapse's first frame. Two causes were found and fixed: the text kept flowing under the blur-out, and the panel put the last answer back in that same frame. Now the reveal stops before the collapse starts, and the restore waits 0.7 s, until the panel has faded out (its one late frame now falls where nothing moves). What is left is 8 to 21 ms in the first frame, against 8 to 10 ms for closing a finished answer. Not yet explained; the next things to look at are the request's cancellation and the spinner still turning under the blur.
- Fixed in slice 2 after review: under a long answer the sources came in below the visible part without the view following them, and clicks on them did nothing until the user scrolled. The cause: an animated change made from outside SwiftUI's own update (`withAnimation` from a queued call) left the scroll view's geometry stale, so its measured height, its bottom fade and its hit-testing all kept the old position. Now those changes are plain assignments and the views animate themselves, the view follows the sources in (unless the reader had scrolled up), and an opened row scrolls fully into view.
- Fixed after San tested (2026-11-25): the body went off-centre while its width sprang. The right edge overshot while the left edge crawled, up to 10 points behind for a quarter of a second. The cause: an animated `frame(width:)` is laid out once at its final width, and SwiftUI then animates the size and the position separately; the size took the edge spring, the position took the slower carrier spring. Now an `Animatable` modifier feeds each in-between width (and height) to layout on every frame (`IslandWidth`, `IslandHeight` in `IslandView.swift`). Measured from filmed frames: left and right are equal in every frame of hover, open, close, the pill and its dismissal, still at 120 Hz.
- [x] Drop-and-save, text only (slice 3, branch `m6-drop-text`, `app/MindDump/Capture/DropModel.swift`): drag highlighted text (or a link from a browser) onto the notch and let go. While the drag is over it, the island opens out and says "Let go to save this note" or "this link", with the note's first words or the link's host and path under the notch. A release saves at once, with no click and no key, through the same code as typed capture (`CaptureModel.store`): "Saved", then the live status, or "Already saved". A drag that leaves or is cancelled saves nothing, and the island goes back to what it showed (a running pill comes back; a status that arrived meanwhile shows then). A failed save opens the panel in Capture with the text in the box and the reason under it, so Return retries. Files, images and blank text are refused (the drag flies back). An open panel is never a drop target: its box takes a drop of text as any macOS text field does (it inserts the text where you let go), in Capture and in Ask. A click elsewhere now closes the panel on release and only if the pointer did not travel, so starting a drag in another app no longer closes it.
- How the drag reaches the island: the window ignores the mouse until the pointer is on the island, and a window that ignores the mouse gets no drags. The pointer tracker's global monitor already watches `leftMouseDragged`, so it flips the window to take the mouse when a drag reaches the notch; AppKit then calls the drop view. While the target shows, the hot zone is the grown body plus 24 points, so it does not flap. A small view of our own sits in front of the SwiftUI content and takes the drops (`DropCatcher` in `NotchWindow.swift`), because the panel's text box keeps its focus while closed, and its hidden editor, which takes text drops, sits right where the target opens. (Letting go of the focus on close was tried and measured: it made the first frame of every later open about 15 ms late.) If AppKit never reports the drag leaving, a watchdog that looks at the mouse button five times a second, only while the target shows, takes it down.
- Tested in slice 3 by debug script verbs that call the same model methods (`drag`, `dragexit`, `drop`, `dragtypes`). A real drag of text from another app was tried by San on 2026-11-25 and saved (item 36 on the throwaway backend), so the global monitor, the window flip, `DropCatcher` and the `DropReceiving` adapter work for a plain text drag. Still untried: Escape during a drag, a release just outside the island, browser link and image drags (which pasteboard types a browser puts on an image drag; a file-promise drag is refused by name), and Finder files. Measured on a 120 Hz display with debug builds: entering the target 0 late frames (13 of 13 runs), leaving it 0 (8 of 8), the release 0 in 4 of 5 runs and one 8 ms late frame in the other; filmed in slow motion, left and right edges are equal in every frame of enter, leave and release, and Reduce Motion eases with no overshoot.
- Known issues (slice 3): a 20,000-character drop that fails (422) opens the panel with all of it in the box, and that open drops about 13 frames while the field lays the text out. The script's `click` from a bare notch misses (the island's button is 1 point tall until the peek grows it); scripts must `pointer notch` first, as a real pointer does.
- [x] Slice 4, layout C "One line" (branch `m6-glass-capsule`, D41): the open black panel is replaced by one Liquid Glass capsule just under the notch, apart from it. The notch stays true black: idle, hover tab and status pills are as before. The capsule is 520 points wide, so a one-sentence question of about 50 characters stays on one line (at 440 a 47-character question wrapped). It is the Capture box (a round mode button, the box, "Save note" or "Save link" beside a ⏎ key cap; once the text comes near the words they fade and a small note or link glyph appears beside the key cap, so there is always a sign of which it is), the Ask box (a round send button in the accent blue) and, for an answer, a card that grows from it (hairline, the question, status, the streamed answer with references, numbered sources, "New ⌘N"). A Capture error adds a second line. A text drag over the notch brings the capsule up as the drop target ("Release to save note" or "link", an accent rim). Closed, the capsule is tucked up inside the notch behind the black body; it springs down and out from under the notch's lower edge and goes back in; on a save it goes in and the "Saved" pill opens. Deployment target macOS 26.0 (Debug and Release); only macOS 26.0 APIs; Debug and Release build with no warnings. `IslandModel` now holds two shapes: `metrics` for the black body (idle, peek, pill) and `capsule` for the glass (tucked, open at its measured height, drop target), both set in its one `apply`.
- How the glass stays readable: `glassEffect(.regular.tint(black 60%))` in a `GlassEffectContainer`, the dark colour scheme, and a 50% black shade inside it while the window is not key (glass in a window that is not key drew lighter: about 135 grey behind the text over the busy backdrop, against 75 to 80 when key). Measured from stills over a white window: open capsule background 70 to 76 grey, drop target 113 (white text about 4.9:1), "Save note" secondary text about 200 on 72. Reduce Transparency (`accessibilityReduceTransparency`, or `MD_REDUCE_TRANSPARENCY=1` in debug builds) makes it a solid dark shape. Controls inside are flat fills, not glass.
- Found while building slice 4: (1) glass applied as a sibling behind the content was drawn over the content by the container; it must be applied to the content view itself. (2) A symbol "replace" effect inside the glass cost 5 to 13 late frames per mode flip; two glyphs that cross-fade and turn cost none. (3) Building a view on a flip (the send button, Ask's section with its scroll view) cost frames; both modes' parts now stay built and only one shows. (4) The box's text editor kept wrapping at an old width when the box changed width under it (a 324-point box whose text still wrapped at 267), so the box now has one width (398 points) in both modes, and Capture's words float over its empty end and fade out when the text comes near them (the note or link glyph takes their place). (6) A streaming answer dropped frames because the glass shape resized on its spring for every new line, not because of the glass: on the same long canned answer, in late frames per second, line by line 2.37 and 2.48; a solid capsule with no glass 2.55 and 2.99; no mask 2.19 and 1.92; glass without the tint 4.75 and 2.29; growing in 60-point steps 1.68 and 1.62; the slice 3 black panel at the same time 1.86 and 2.44. So while an answer streams the card grows in 60-point steps (about three lines) and fits its content exactly once the answer is complete; the text pours as before. In its final form: 2.02, 2.41 and 1.11 (mean 1.85). (5) AppKit's first text focus cost 55 to 58 ms inside the glass; the box now takes the focus once at launch, out of sight.
- Removed at San's request on 2026-11-25: the clipboard offer (slice 1's "Return saves the link on your clipboard"). The app no longer reads the clipboard; an empty box saves nothing. A link pasted into the box with ⌘V is sorted like typed text.

Under `MD_REDUCE_MOTION=1` the capsule fades in and out where it opens (its top edge at the same row in every filmed frame) and nothing overshoots.

- [x] Slice 5, drop a file (branch `m6-file-drop`): drag one PDF, PNG or JPEG onto the notch and let go. While the drag is over it, the glass target says "Release to save file", with a document glyph and the file's name under the words (shortened in the middle, so the start and the extension stay). Only the name, type and size are looked at while hovering; the bytes are read only after the release. The release uploads the file to `POST /items/upload` (raw bytes, the name in `Content-Disposition`; a name that is not plain ASCII goes in the `filename*=UTF-8''…` form), and the pill goes "Saved", then "Processing", then "Ready" (or "Couldn't process"), through the same code as notes and links (`CaptureModel.announce`, `follow`). The same bytes again say "Already saved" and make no second item. Turned down before any upload, with the reason in the target and a grey "no" glyph and rim (the drop is refused, so the file flies back): not a PDF, PNG or JPEG by its type or extension, a folder ("Only PDF, PNG and JPEG files"), over 25 MB ("Too big: 25 MB at most"), an empty file, several files ("One file at a time"). After a release, the backend's 415 and 413 and a backend that is down give a warning pill for 3 seconds ("Only PDF, PNG and JPEG", "Too big: 25 MB at most", "Backend isn't running"); the capsule does not open (a text box cannot hold a file), and the file is untouched where it was. The upload is streamed from disk by `URLSession.upload(for:fromFile:)`, off the main thread. A drag that carries a file and text (Finder does this) is a file. Pills may now be a little wider (each wing up to 170 points, from 132) so these warnings fit; shorter pills are unchanged.
- How a dragged file is read in the sandbox: the app has only the sandbox and network-client entitlements, and needs no new one. A file URL on a drag pasteboard carries a sandbox extension that the system grants to the app that reads it (`readObjects(forClasses: [NSURL.self])` in `DropModel.payload(from:)`), for as long as the app runs. The upload also opens the URL's security scope in case it has one. This is Apple's documented drag-and-drop behaviour, but it is not tried yet: the script tests use files in the app's own container, which the sandbox always allows.
- Tested in slice 5 by debug script verbs that call the same model methods (`dragfile <path>`, `dropfile [<path>]`; several paths separated by " | "). Against the throwaway backend: a one-page PDF saved as item 55 (`media_type` application/pdf, 639 bytes, `filename` heron-note.pdf, `sha256` equal to `shasum -a 256`), "Saved", "Processing", "Ready"; the same PDF four more times, "Already saved" and no new item; an 8 by 8 PNG saved as item 57, "Ready" after Claude described it; a text file named `.pdf`, a 415 and the warning pill; a 20 MB PDF uploaded in about 125 ms with no late frame while it went (it is zeros after the header, so the worker marked it "Couldn't process", as it should). The app pointed at an unused port: "Backend isn't running", no capsule. A local stub that waited 1.2 s and answered 503: the target said "Saving…" from 0.3 s, then "Couldn't save the file". Not tried: a real drag from Finder (only that drag runs `DropCatcher`, `IslandHostingView`'s drag methods, the `DropReceiving` adapter and `payload(from:)`), a file promise drag (Photos, Mail attachments), JPEG (it takes the same path as PNG), a name with a slash or colon.
- Measured on a 120 Hz display with debug builds (load average about 3, the same busy Mac as slice 4): a file's target in 0 late frames in 11 of 13 runs and one 8 ms frame in the other two; out 0 in 4 of 5 and one 8 ms frame; a refused file's target in 0 (3 of 3), out one 8 ms frame each (3 of 3); a text target in 0 in 4 of 5 (one 8 ms frame), out 0 (4 of 4).
